为什么 mcptoon 坚持做原生 CLI，而不是常驻守护代理？

MCP 的设计假设是“每项能力都是一台服务器”，逼迫开发者必须在每个客户端手写不同的 JSON 格式挂载。这带来了无休止的配置漂移和端口冲突。

零额外开销架构

传统常驻代理模式的弊端

  • 必须针对 Claude、Cursor、Windsurf 分别手写并维护不同格式的 JSON 配置
  • 增加常驻后台守护进程，面临端口冲突、进程僵死、显存或内存静默泄漏风险
  • 未输入 Prompt 之前，必须把成千上万行的 Schema 静态数据先硬塞给模型
  • 一旦新增或修改工具，必须将所有客户端的 JSON 配置重新同步编辑一遍

mcptoon 极简 CLI 架构

  • 42+ 款终端与 IDE Agent 零配置：Cursor、Claude Code、Codex 只要敲 mcptoon call 即可开箱即用
  • 一份全局配置全端共享：在 mcptoon 中装一次，本机所有智能体立刻自动识别
  • 无常驻守护、无常驻开销：纯 Python 标准库编写（仅 363KB），随调随跑，执行完毕即退出释放内存
  • 无缝兼容 61 款纯 GUI 客户端：对无法执行 Shell 的纯聊天客户端，提供轻量 mcptoon serve 统一桥接

常见问题解答

为什么说 CLI 比常驻后台代理（Proxy）更好？

常驻后台代理仍然需要你手动在每个客户端里配置主机名、端口与 Header。而 CLI 充分利用了每一个编程 Agent 天生就具备的能力：终端命令行调用。Agent 直接通过命令行执行 mcptoon call，既不需要为每个客户端重复配置 JSON，也彻底避免了后台内存泄漏、僵尸进程与端口冲突。

mcptoon 是如何同时统筹 MCP 工具与 Agent 技能的？

mcptoon 提供双轨统一治理：针对 MCP 工具，将 Schema 缩减为极简名字索引（省 99.2% Token），按需拉取参数；针对技能，摒弃把数百个 SKILL.md 全量加载进上下文的做法，改用 39 Token 的极简常驻指针，搭配本地离线 BM25 路由在 5ms 内按需调取目标手册。

我需要手动重新配置所有的 Agent 吗？

完全不需要。执行 mcptoon quickstart 会自动扫描你机器上已安装的 Agent（Cursor、Claude Code、Windsurf、Cline 等）与已配置的 MCP 服务，生成统一配置并自动将 /mcptoon 官方技能注入各个 Agent 目录。后续在 mcptoon 中统一增删，多端立即生效。

是否有任何数据上传到外部云端或第三方服务器？

绝对没有。mcptoon 100% 本地运行且开源（Apache-2.0），没有任何远程遥测、统计追踪或后台网络请求。
